# 大模型汉化效果优化：人工译文对照与首轮改进

调研日期：2026-10-29。重点是语义、中文表达、角色口吻和歌词意象；格式检查只是底线。
本文保留首轮调研及来源记录；后续已完成生产模型的 90 组对照试译、提示词落地和少量机器译文修订，见 [第二轮实施与实测结果](TRANSLATION_QUALITY_RESULTS_20261029.md)。没有全库重译或将网络译文自动晋级为正式成果。

## 仓库与真实生产入口

| 仓库 | 负责的内容 | 优化应落在哪里 |
| --- | --- | --- |
| MLTDTranslationAssets | 剧情、卡片、日常对话、邮件、歌词、图片、术语；自动翻译和资源发布 | 主要实施仓库：模型输入、提示词、人工对照、审校 |
| MLTDTranslationClient | APK 内置文字、字体、图集和公开安装包 | 同步使用共享翻译器；按界面长度做单独评测 |
| MLTDTranslationPortal | 搜索、阅读、歌词版本和原译文对照 | 后续提供完整场景审核和译文问题反馈 |

现行文字生产链为 `llm-translate-assets.yml` → `scripts/llm_translate_untranslated.py collect`
→ `pipelines/text/translate_mltd_api_pool.py` → apply / publish → 仓库校验和资源构建。
系统提示词来自 `pipelines/text/mltd_translation_prompt.py`，权威术语来自 `glossary/authoritative-terms.json`。
`accepted` 表示可进入构建，不能等同于人工质量验收；`translation_stage` 缺失的历史数据也不能直接标成人工翻译。

`research-tools/` 保留了官方历史译文 benchmark、上下文和审校工具，但没有接入当前生产 CI。
本轮直接运行其中 `evaluate_translation_benchmark.py --help` 遇到旧导入路径错误；不能把归档能力当作现行发布门禁。

可重复的离线比较命令（输出含参考全文，保存在本地研究目录）：

```powershell
python scripts/audit_human_lyrics.py --reference-cache '<采集器的cache目录>' --output '<仓库外的研究目录>/human-lyric-comparison.json'
```

该脚本只生成审核队列，不调用模型、不写汉化源文件、不把措辞差异算成错误率；所有条目初始 `gold_eligible=false`。

## 从抽样得到的模型问题

从已对齐且措辞不同的记录中，以 source SHA-256 的稳定哈希排序抽取 20 条作探索性阅读；这不是独立盲测。
人工参考也有生硬或增译的例子，所以以日文判断语义，用人译发现更好的表达，不以相似度排名。

以下建议由本轮审读提出，未直接替换正式译文，也不是复制参考译文：

| 现行表述或现象 | 需要检查的点 | 建议方向 |
| --- | --- | --- |
| “确认着你的睡脸” | 日文动作被机械映射成不自然的中文搭配 | 根据场景选“看着你熟睡的脸”等自然动作；不从参考中追加时间信息 |
| “板着认真的表情” | 把认真补成不悦、严肃甚至责备 | “一脸认真”等，保留程度，避免额外情绪 |
| “能让大家展露笑容” | 共同体验被改成使役关系 | 原文若是与大家一起欢笑，就保留共同体验 |
| “直到声嘶力竭，也要继续……” | 终点条件被写成让步，可能暗示超过终点仍继续 | 保留“唱/喊到……为止”的时间关系 |
| “手工制作舞台” | 忽略歌曲中共同经营、打造舞台的意象 | 在原文允许时用“亲手打造舞台”，不引入额外故事解释 |
| 中文已经表达“准备好了”，后面又接 OK | 中英混合句被重复解释 | 固定副歌保留其功能，同一意思只表达一次 |

参考中某句比当前译文更长、更华丽，不表示更准确。应保留原文中的主体、否定、威胁、犹豫、
反语和画面感，避免补出“我们”“每一株”“帅气”等日文与上下文未建立的信息。

## 首轮已实施的模型输入与提示词改进

1. **歌词真正进入歌词任务。** 采集器原本写入 `task=ASSETS_LYRICS`，翻译器却只看 `task_hint` 和通用启发式。
   现在明确识别该任务，执行歌词单槽、意象、视角、跨槽句法和英文副歌规则。
   公共 preset 显式提供歌词参数（通用意图为 low / 2048）；第二轮实测生产别名拒绝 low，已配置启用推理时的 high 下限，保留显式 none。
2. **传递源语上下文。** 为同场景连续编号的台词和按索引排序的歌词提供日文语境；首轮前后一个槽，第二轮扩大至前后三个槽并附各句说话者代码，最多保留三个用例。
   不把已有中文作为暗示答案。master 增量清单不保证完整顺序，不把相邻行拼成剧情。
   台词编号跳跃时也不跨接，避免把不同分支或缺失片段误作上下句。
3. **恢复人物身份。** 生产 workflow 从 `glossary/idols.json` 生成身份信息，替代原来的空 speakers 字典。
   只提供身份，不凭角色名强加口癖、性格或地方腔。
4. **正确识别邮件。** 从明确的邮件 key 提取作者，提供 `SURFACE=MAIL`，保留书信语气和段落。
   当前三条待译邮件已由 DESCRIPTION 改为 DIALOGUE / MAIL / 051tmg；不同回复分支不互相当上下句。
5. **针对真实语言问题做内部修订。** 提示模型先判断话语功能，再校验共同/使役、终点/让步、
   威胁/中性、认真/不悦等区别，最后修正中文搭配；只输出最终译文。
   短例句是自行构造的决策示例，明确不冒充人译或官方术语。
6. **复用句不受第一个场景支配。** 汇总人物和使用类别，多场景句提供源语用例，要求选共同支持的译法。
   暂时保留 source-hash 的单译文存储契约，真正需要按语境分译的情况进入后续改造。

首轮保留机器草稿来源、已有人工成果和已发布内容；第二轮仅修订三个明确标记为机器翻译的歌词槽，没有全量重译。
首轮未找到可用调用配置；后续复核找到了本地配置，已完成对照试译。Agent 逐条审读与部分模型偏好结果均不等于人工准确率，没有质量提升百分比。
代码回归和真实数据校验只能证明链路可用，不能代替译文效果验收。

| P1 | 用完整新抽取场景补上下文，避免增量清单断章 | 为新 GTX/邮件保留源语场景或分支侧车数据；邮件回复按分支关系取父消息，不能按文件行号猜 |

| P1 | 对高风险句做第二遍独立审校 | 否定、主体省略、反语、双关、分槽歌词和术语冲突优先；审校器回报具体问题，最多定向重译一遍，不为小词差异无限重试 |
| P1 | 固定分层盲测集 | 初期目标 200 歌词 / 400 剧情、邮件与对话 / 100 UI。按整曲、整章和归一化原文去重，保留整组留出集；旧版官方译文与现代人译分开统计 |
| P2 | 将审核反馈接回查阅站 | 显示整个日文场景、现译、候选、人工证据和具体错误类别；保存审定理由，不只收集喜欢哪句话 |
| P2 | 若试点仍暴露歧义复用问题，再扩展译文身份 | 由 source hash 扩为 source + surface + scene identity；协调生成器、歌词复用和查阅站，防止仅改提示词却被全局记忆重新覆盖 |

主要指标按体裁报告：误译、漏译、增译、主体/对象、否定与条件、术语、口吻、中文自然度、歌词意象与跨行连贯。
严重语义错误优先于文风偏好；字面相同率、覆盖率、QA 通过率和模型自评分都不能直接叫准确率。

如果只改了提示词，先用相同上下文做 A/B，测提示词贡献；再单独加入新上下文，测输入贡献。
模型升级作为第三组实验，避免把提示词、上下文、模型和采样参数同时变更后无法归因。
